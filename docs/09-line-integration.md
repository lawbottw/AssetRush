# 09 — LINE Mini App 整合與群組資料

> 文件版本 v0.1｜2026-08-06
> 本文件涵蓋 LINE Mini App 的申請、設定、群組開局、資料導入的界線、以及送審流程。

---

## 1. 為什麼需要獨立一份文件

LINE 整合有兩個特性讓它不適合塞在架構文件裡：

1. **有大量非技術的行政流程**（官方帳號認證、Verified Mini App 審查、shareTargetPicker 開通），而且**這些流程會卡開發進度**——必須提早啟動。
2. **群組資料的取得有嚴格界線**，而這個界線常被誤解（很多人以為「拿得到群組成員名單」）。搞錯會導致整個開局流程要重做。

---

## 2. 最重要的一件事：LINE 不會給你群組成員名單

**這是整份文件最需要先講清楚的限制。**

很多人對「嵌入 LINE 群組」的想像是：機器人進群 → 讀取成員清單 → 自動幫大家開局。

**這做不到，而且不該做。**

| 你以為拿得到 | 實際上 |
|---|---|
| 群組成員名單 | ❌ 拿不到完整名單（Messaging API 的 group member IDs 端點僅限已驗證帳號，且只回傳「已加此官方帳號為好友」的成員） |
| 每個成員的名字與頭像 | ❌ 只有主動點進 Mini App 的人才會授權 |
| 群組名稱 | ⚠️ 有限度取得，需已驗證帳號 |
| 群組 ID | ✅ 可取得（`liff.getContext().groupId`） |
| **點進來的那個人的 userId** | ✅ 這是唯一穩定可用的身分 |

### 2.1 因此開局流程必須是「拉」而非「推」

```
❌ 錯誤設計（做不到）
   房主開局 → 系統讀取群組 20 人 → 自動建立 20 人的局

✅ 正確設計
   房主開局 → 系統產生一張 Flex Message 邀請卡 → 貼進群組
            → 每個人自己點進來 → 授權 → 加入
```

**`groupId` 的角色是「局的容器」，不是「成員名單」。**

同一個 `groupId` 開的所有局會被歸在一起（可看群組歷史戰績），但**誰在局裡完全取決於誰主動點了那張卡**。

這其實與[產品設計](00-product-overview.md#4-局的獨立性)是一致的——我們本來就要求玩家主動加入，而不是被拉進一個他沒同意的遊戲。

### 2.2 這對報名階段的影響

| 設計決策 | 理由 |
|---|---|
| 報名階段要有明確的「等待中」畫面與人數顯示 | 房主看不到誰還沒點，需要知道現況 |
| 提供「再催一次」按鈕，重貼邀請卡 | 取代不存在的「自動邀請」 |
| 房主可隨時手動開始，不必等滿 | 永遠不會「全員到齊」 |
| 開局後仍允許中途加入（限日常型前 3 天） | 群組裡總有人晚看到訊息 |

**中途加入者的起始資產**：依[家境抽取](02-game-balance.md#1-家境抽取)正常抽，但現金額外 `× (1 + 已過天數 × 0.15)`，補償落後的圈數（21 天局的第 3 天加入 → ×1.45）。

## 3. 申請與設定流程

### 3.1 帳號層級

```
LINE 官方帳號（LINE Official Account）
   └─ 通過 官方帳號認證（OAV）→ 認證帳號（藍盾）
        └─ LINE Developers Console 建立 Provider
             └─ 建立 LINE MINI App Channel
                  └─ 送審 → Verified MINI App
             └─ 建立 Messaging API Channel（推播用）
```

### 3.2 ⏰ 會卡進度的兩件行政流程

| 項目 | 前置條件 | 建議啟動時機 |
|---|---|---|
| **官方帳號認證（OAV）** | 需公司登記或個人身分文件、營業證明 | **P0 就送出** |
| **Verified MINI App 審查** | 需先有認證帳號 + 符合發布規範 | **P4 送出**（不要等 P6） |
| **shareTargetPicker 開通** | 需逐 channel 申請並同意 LIFF 使用條款 | **P4 送出** |

**這三件事都不是技術問題，但都會讓 P6 卡住。** 路線圖把它們標為 P4 就要啟動，就是這個原因。

未認證期間可用 **Unverified MINI App** 開發與測試，功能大致相同，但：
- 不會出現在 LINE 的 MINI App 目錄中（無自然曝光）
- 部分 API 受限
- 無法使用 In-App Purchase

### 3.3 LIFF 設定

| 設定項 | 值 | 說明 |
|---|---|---|
| Size | **Full** | 遊戲需要最大可視區域 |
| Endpoint URL | `https://<domain>/liff` | 對應 `app/(liff)/` 路由群組 |
| Scope | `profile`, `openid` | 只要最小必要 |
| Bot link feature | **On (Aggressive)** | 加入 Mini App 時同步加官方帳號好友——**推播的前提** |
| shareTargetPicker | On | 需另外申請 |
| Module mode | Off | v1 不需要 |

**`Bot link feature` 必須開 Aggressive**，否則玩家沒有加官方帳號好友，[每日戰報與提醒推播](01-game-rules.md#143-每日-0000-結算)就送不出去——而那是日常型模式的命脈。

### 3.4 環境變數

```bash
LIFF_ID=                      # LIFF app ID
LINE_CHANNEL_ID=              # MINI App channel
LINE_CHANNEL_SECRET=
LINE_MESSAGING_CHANNEL_TOKEN= # Messaging API，推播用
LINE_MESSAGING_CHANNEL_SECRET=
NEXT_PUBLIC_LIFF_ID=          # 前端需要
```

## 4. 登入與身分

### 4.1 流程

```
1. LIFF 初始化（client-side，見 06 風險 4）
2. liff.isLoggedIn() → 否則 liff.login()
3. liff.getIDToken()  取得 ID token
4. 送到 Next.js BFF
5. 後端向 LINE 驗證 ID token（POST https://api.line.me/oauth2/v2.1/verify）
6. 取出 sub（= LINE userId）
7. 對照 users.line_user_id → 找到或建立帳號
8. 簽發 Supabase JWT
```

**第 5 步的伺服器端驗證不可省略。** 前端傳來的 ID token 必須向 LINE 驗證簽章與 audience，否則任何人都能偽造身分。

### 4.2 雙軌帳號合併

同一個人可能先用 LINE 玩、後來用網站登入。

```
users
  id             uuid  (PK)
  line_user_id   text  unique nullable
  email          text  unique nullable
```

合併規則：
- 已登入 LINE 的使用者綁定 email → 更新同一列
- 已有 email 帳號的使用者用 LINE 登入 → 若 LINE userId 未被使用，綁上去；若已被別的帳號使用，**要求使用者選擇保留哪一個**（不自動合併，避免資料錯置）

合併時進行中的局如何處理：**不允許在有進行中的局時合併帳號**。提示使用者等該局結束。這比實作局資料的搬移簡單得多，而且發生頻率極低。

## 5. 群組開局

### 5.1 取得 groupId

```ts
const ctx = liff.getContext();
// ctx.type: 'utou' | 'room' | 'group' | 'square_chat' | 'external' | 'none'
// ctx.groupId: 僅當 type === 'group'
```

| context type | 意義 | 我們的處理 |
|---|---|---|
| `group` | 從群組開啟 | ✅ 綁定 `games.line_group_id` |
| `room` | 從多人聊天室開啟 | ✅ 同上，用 `roomId` |
| `utou` | 一對一聊天 | 視為個人局，不綁群組 |
| `external` | 從外部瀏覽器開啟 | 走獨立網站流程 |
| `none` | 無 context | 走獨立網站流程 |

**`ctx` 只在 Mini App 從該對話開啟時才有值。** 玩家從 LINE 主畫面的「MINI App」清單進來時 `type` 會是 `none`——這時要顯示「我的對局」清單讓他選，而不是報錯。

### 5.2 群組層的資料

我們對一個群組**只存 `groupId` 與它開過的局**，不存成員名單（也拿不到）。

```sql
-- 見 05-data-model.md
games.line_group_id  text
```

由此可衍生的功能：

| 功能 | 實作 |
|---|---|
| 群組歷史戰績 | `SELECT ... FROM games WHERE line_group_id = ?` |
| 群組總排行榜 | 聚合該群組所有已結束的局 |
| 「上次那群人再來一局」 | 從上一局的 `game_players` 取 user list，發個人推播邀請 |

**最後一項是取代「讀取群組成員」的正解**——我們不知道群組裡有誰，但我們知道**上一局有誰**，而那才是真正會回來玩的人。

## 6. Flex Message

三種卡片，全部由後端組 JSON、經 Messaging API 或 `shareTargetPicker` 送出。

### 6.1 邀請卡（開局）

```
┌────────────────────────────┐
│ 🎲 AssetRush               │
│ 阿宏 開了一局「日常型」      │
├────────────────────────────┤
│ 模式：日常型（每天 3–5 分鐘）│
│ 上限：30 人 · 21 天          │
│ 目前：6 / 30 人已加入        │
│ 棋盤：標準局（全台 36 格）   │
├────────────────────────────┤
│      [  加入這一局  ]        │
└────────────────────────────┘
```

按鈕的 URI 是 `https://liff.line.me/<LIFF_ID>?game=<game_id>`。

### 6.2 每日戰報（群組推播）⭐

**非同步改制後最重要的社交鉤子。** 每天 00:00 結算後推播到群組。

```
┌────────────────────────────┐
│ 📰 「大學同學會」第 12 天    │
├────────────────────────────┤
│ 🔨 昨日成交                 │
│   信義區 → 小美 $520,000    │
│   （阿宏出 $480,000 落敗）  │
│   鹿港鎮 → 志明 $72,000     │
│ 💸 最大一筆租金             │
│   大雄 → 小美 $186,000      │
│ 💀 大雄 破產                │
├────────────────────────────┤
│ 🥇 小美 $3,180,000          │
│ 🥈 阿宏 $2,410,000          │
├────────────────────────────┤
│  8 / 12 人已完成今天         │
│      [  去玩今天  ]          │
└────────────────────────────┘
```

**它取代了第一版的「輪到你了」個人提醒。** 差別在於：個人提醒只對一個人有意義，戰報給了**整個群組共同的話題**——「欸阿宏你昨天輸掉信義區喔」。

競標落敗會被寫進戰報，是刻意的——那是最有戲的一刻。

### 6.3 未行動提醒（個人推播）

送給**個人**而非群組——群組裡每天 30 則提醒會被退群。

```
┌────────────────────────────┐
│ ⏰ 今天還沒玩              │
│ 「大學同學會」第 12 天       │
│ 距離 00:00 結算剩 4 小時     │
│ ⚠ 你對鹿港鎮的出價將被仲裁   │
│      [  去玩今天  ]          │
└────────────────────────────┘
```

推播頻率上限：**每人每局每天 2 則**（群組戰報 1 則 + 未行動提醒 1 則）。被託管後額外 1 則結果通知。

**推播節制是留存問題，不是禮貌問題。** LINE 使用者對推播的容忍度極低，封鎖官方帳號的成本是零。

非同步改制降低了推播需求——第一版需要「時窗前 15 分鐘」「輪到你了」兩則精準提醒，現在只需要一則「今天還沒玩」。

### 6.3 戰報卡（局末）⭐

**這是產品的主要擴散點。**

```
┌────────────────────────────┐
│ 🏆 「大學同學會」完局        │
│ 21 天 · 12 人 · 21 圈        │
├────────────────────────────┤
│ 🥇 小美  $8,420,000         │
│ 🥈 阿宏  $6,110,000         │
│ 🥉 志明  $4,890,000         │
├────────────────────────────┤
│ 💸 最大一筆租金              │
│    志明 → 小美  $186,000     │
│    （信義區 商辦）           │
│ 🔨 最激烈的搶標              │
│    信義區 · 4 人競標         │
│    小美 $520,000 勝出        │
│ 💀 最早破產：大雄（第 6 天）  │
│ 📈 股神：阿宏 +$420,000      │
│ 💍 本局唯一夫妻：小美 & 阿華  │
├────────────────────────────┤
│  [ 分享 ]      [ 再來一局 ]  │
└────────────────────────────┘
```

素材全部由 `game_events` 事件流一句 SQL 撈出（見 [05 §5.2](05-data-model.md#52-為什麼要事件溯源)）——**這是當初決定做事件溯源的主要理由。**

**「最激烈的搶標」是認購制帶來的新素材**：`bid_*` 事件流天然記錄了每一次競標的參與者與價格，這在第一版的「立即成交」下不存在。

「分享」按鈕呼叫 `liff.shareTargetPicker()`，可送到其他群組——這是跨群組擴散的唯一路徑。

## 7. 技術限制與對策

> 架構層的完整風險清單見 [06](06-architecture.md)。此處只列 LINE 特有的。

| # | 限制 | 對策 |
|---|---|---|
| 1 | LIFF SDK 需要 `window`，SSR 會爆 | `app/(liff)/` 全 CSR，`dynamic import`（[06 風險 4](06-architecture.md#風險-4--liff-必須-client-side-初始化)） |
| 2 | iOS WKWebView session 掉失 | `SameSite=None; Secure`；備援用 `liff.getIDToken()` 靜默重新交換（[06 風險 5](06-architecture.md#風險-5--ios-line-webview-的-session-掉失)） |
| 3 | 可視高度比一般瀏覽器小 | 手機用捲動長條 + 迷你環（[03 §6.2](03-map-system.md#62-手機直式捲動長條--迷你環)） |
| 4 | LIFF 初始化 300–800ms 空白 | 純 CSS 棋盤 skeleton 立即渲染 |
| 5 | 使用者隨時被 LINE 訊息打斷 | 狀態全在伺服器，回來無縫接續 |
| 6 | `shareTargetPicker` 需 LINE 10.13.0+ | 偵測版本，過舊則降級為「複製連結」 |
| 7 | Flex Message 不支援 CSS 變數 | 建置時由 `globals.css` 產生 `theme.flex.json`（[07 §8.1](07-design-system.md#81-戰報-flex-message)） |
| 8 | 深色模式跟隨 LINE 而非系統 | 讀 `liff.getContext()`，並提供手動切換 |
| 9 | 無法取得群組成員名單 | 見[第 2 節](#2-最重要的一件事line-不會給你群組成員名單) |

## 8. 送審準備

Verified MINI App 審查會檢查的項目（依 LINE MINI App 平台使用條款與發布規範）：

| 項目 | 我們的狀態 |
|---|---|
| 服務條款與隱私權政策頁面 | 需準備（P6 前） |
| 明確的服務說明 | ✅ |
| 不得誘導加好友後立即封鎖 | ✅ Bot link 是為了回合推播，有實質功能 |
| 虛擬貨幣不可兌現 | ✅ 明確設計為不可儲值／提領／轉讓（[04 §7](04-economy-and-realdata.md#7-合規注意事項)） |
| 金融資訊的免責聲明 | ✅ 股市介面固定顯示 |
| 未成年保護 | 需評估——遊戲含金融內容與內購 |
| 個資蒐集告知 | 需準備（我們只存 LINE userId 與顯示名稱） |

### 8.1 需要額外評估的兩點

**未成年保護**：遊戲有股票、貸款、破產等內容，且有內購。雖然全部是模擬、不涉真實金錢投資，但仍建議：
- 分級標示（建議 12+）
- 內購前的年齡確認
- 民間信貸等高風險內容加註警語

**「不構成投資建議」的呈現位置**：不能只放在服務條款裡，必須在股市介面本身固定可見。

## 9. 開發與測試

| 需求 | 方式 |
|---|---|
| 本機開發 | `ngrok` 或 Cloudflare Tunnel 提供 HTTPS endpoint，填入 LIFF Endpoint URL |
| 多環境 | 建 dev / staging / prod 三個 LIFF app，各自 endpoint |
| 桌機除錯 | LIFF Inspector；但 `getContext()` 在桌機恆為 `external` |
| **iOS 真機測試** | **無法省略**——WKWebView 的 cookie 行為無法用桌機模擬 |
| 群組情境測試 | 需建測試群組並實際貼卡片 |

### 9.1 P6 的驗收條件

```
從 LINE 群組貼邀請卡
  → 5 個人各自點進來、授權、加入
  → 開局
  → 跑完一局
  → 戰報分享到另一個群組
全程無阻礙。

且：iOS 真機 24 小時後回來，session 仍在。
```

最後一項是最容易在上線後才炸的——**必須真機測，且必須跨日測**。

## 10. 與獨立網站的關係

| | LINE Mini App | 獨立網站 |
|---|---|---|
| 角色 | **獲客** | **留存** |
| 渲染 | 全 CSR | SSR + RSC |
| 登入 | LIFF ID token | Email / Google |
| 開局來源 | 群組 | 個人／配對 |
| 分享 | Flex Message | OG image + 連結 |

**兩者共用同一套 component 與同一個 FastAPI。** 差異只在資料取得方式與 auth 來源——這是用路由群組（`(web)` / `(liff)`）而非兩個專案的原因。

從 LINE 進來的玩家玩上癮後，會自己去裝網站版（桌機體驗更好）；從網站進來的玩家想找朋友玩時，會回頭用 LINE 開局。這個循環是雙軌策略的目的。
