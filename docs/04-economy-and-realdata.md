# 04 — 真實數據接入

> 文件版本 v0.1｜2026-08-06
> 本文件回答使用者提出的問題：**哪些數據需要即時、哪些不需要、怎麼接、怎麼映射。**

---

## 1. 資料即時性分級

這是整份文件最重要的一張表。**專案的技術複雜度幾乎完全由這張表決定**——如果所有東西都要即時，架構會貴 10 倍。

| 資料 | 即時性 | 更新頻率 | 來源 | 失效影響 |
|---|---|---|---|---|
| 股票收盤價 | **日更（T+1）** | 每交易日 15:00 後 | TWSE OpenAPI | 遊戲股價停止更新，可 fallback |
| 台股是否開市 | **日更** | 每日 08:00 檢查 | TWSE 回傳有無資料 | 日常型股市誤開/誤關 |
| 鄉鎮房價 | **季更** | 每季一次 | 內政部實價登錄 | 幾乎無影響（局內已固化） |
| 薪資統計 | **年更** | 手動 | 主計總處 | 無（寫死在 config） |
| 家庭財富分配 | **不更新** | 手動 | 主計總處 | 無（寫死在 config） |
| 遊戲局狀態 | **即時** | 每個動作 | 自己的 DB | 遊戲無法進行 |

**真正需要「即時」的只有遊戲自己的局狀態。** 所有真實世界的數據都是日更或更慢。

這個結論很重要，因為它意味著：
- 不需要付費行情源
- 不需要 WebSocket 串接外部服務
- 不需要處理盤中斷線、延遲揭露規範
- 外部資料源全掛掉時，遊戲仍然可以完整進行
- **開發期完全不需要跑爬蟲**——用 [§3.6](#36-開發期的種子資料) 的真實收盤快照即可

## 2. 股票標的

### 2.1 資料源（已實測驗證）

```
GET https://openapi.twse.com.tw/v1/exchangeReport/STOCK_DAY_ALL
```

- **免費、無需 API key、無需註冊**
- 回傳當日**全市場**個股 OHLCV
- 實測回傳欄位：

| 欄位 | 型別 | 說明 |
|---|---|---|
| `Date` | string | 民國年 `YYMMDD`（如 `1150805`） |
| `Code` | string | 證券代號 |
| `Name` | string | 證券名稱 |
| `TradeVolume` | string | 成交股數 |
| `TradeValue` | string | 成交金額 |
| `OpeningPrice` | string | 開盤價 |
| `HighestPrice` | string | 最高價 |
| `LowestPrice` | string | 最低價 |
| `ClosingPrice` | string | 收盤價 |
| `Change` | string | 漲跌**價差**（非百分比） |
| `Transaction` | string | 成交筆數 |

**重要限制：**
- 只回傳**單日**資料，且是 **T+1**（今天拿到的是昨天的）
- 歷史序列必須**自己每天抓下來存**——沒有歷史查詢端點
- 所有數值都是 string，需自行轉型
- **`Change` 是價差不是漲跌幅**，漲跌幅必須自己算：`Change / (ClosingPrice - Change)`
- 停牌或無成交的個股，價格欄位可能是 `"--"` 或空字串，**必須做防禦性解析**
- 無 SLA、無穩定性保證

### 2.2 標的清單（50 檔）

**沿用真實代號與名稱。** 選 50 檔而非全市場，理由：

- 全市場 1,800+ 檔會讓玩家決策癱瘓，且大多數是玩家沒聽過的公司
- 50 檔剛好能塞進一個可捲動的清單，且涵蓋主要產業與 ETF 風格
- 資料量小，`stock_prices` 一年只長 50 × 245 ≈ 12,250 列

### 2.3 為什麼用真實代號

1. 代號與名稱是公開資訊
2. 遊戲內是模擬持股，**不可儲值、不可提領、不可轉為法幣**
3. 一律 T+1，不提供盤中報價，不提供任何買賣建議
4. 用真名才有「台積電漲停我也賺翻」的話題性——這是產品最強的社群鉤子

仍需在股市介面**固定顯示**：「本遊戲內容純屬娛樂，不構成任何投資建議」。必要的合規動作，成本極低。

## 3. 價格

### 3.1 直接使用真實股價，不做映射

```
遊戲內股價 = 該檔的真實收盤價（前一交易日，T+1）
```

台積電在遊戲裡就是兩千多塊一股，中鋼就是十幾塊。

> **這是對前一版設計的修正。** 前一版採「所有標的統一基準價 $1,000 + 套用真實漲跌幅」，理由是擔心真實股價的絕對值與遊戲資產尺度不匹配。**實測後發現這個擔憂是錯的**——因為最小交易單位是「股」而非「張」。

### 3.2 尺度驗證

以普通家庭起始現金 $180,000 計（價格為 2026-08-05 真實收盤）：

| 標的 | 真實價 | 買得起 |
|---|---|---|
| 2454 聯發科 | $4,000 | 45 股 |
| 2330 台積電 | $2,405 | 74 股 |
| 006208 富邦台50 | $238.25 | 756 股 |
| 0050 元大台灣50 | $103.80 | 1,734 股 |
| 00981A 主動統一台股增長 | $28.46 | 6,323 股 |
| 2002 中鋼 | $18.90 | 9,523 股 |

**最貴的標的也買得起 45 股，最便宜的可買近萬股。** 尺度成立。

改用真實價換來的好處：

| 好處 | 說明 |
|---|---|
| 沉浸感 | 「我買了 100 股台積電」比「100 單位的虛擬台積電」真實得多 |
| 少一層抽象 | 不需維護映射層，不會出現「遊戲裡漲了但真實跌了」的對不上 |
| 除錯容易 | 玩家看到的數字就是資料庫裡的數字 |

代價是**每局的起手價不同**（同一群朋友這個月玩和下個月玩，台積電價格不一樣）。但這其實是真實的，且因為所有玩家在同一局面對同一組價格，局內公平性不受影響。

### 3.3 何時能交易：季度事務

**股票不是棋盤格，也沒有時窗。** 交易併入通過起點的[季度事務](01-game-rules.md#18-季度事務)——一圈一次，就是你回到起點時順手做的一件事。

證交所格已從棋盤移除。

> **這是對前兩版的修正。** 第一版用「全域 90 秒開盤鐘 / 對齊真實 09:00–13:30」，第二版改「過起點後 2 小時個人時窗」。兩者都有問題：前者要協調所有人，後者仍有時限壓力（「我上線時剛好過期」）。
>
> 現在完全沒有時限——**你什麼時候玩，什麼時候就是你的開盤時間。**

**日常型下三件事天然對齊：**

```
1 天  =  1 圈  =  1 次季度事務  =  1 次 T+1 價格更新
```

每天恰好一次交易機會，不早不晚，也不需要盯任何時鐘。這個對齊不是巧合——它是「[一日一季](01-game-rules.md#42-日常型一日一季)」與「T+1 定價」兩個決定共同推導出來的結果。

即時配對型的季度事務是**非阻塞側欄**，可在別人回合時處理，不卡住牌桌。

### 3.4 價格何時推進

**兩種模式規則一致：每圈推進一個真實交易日。** 休市日沿用前一交易日收盤價。

| 模式 | 說明 |
|---|---|
| 日常型 | 1 圈 = 1 天，天然對齊真實日曆 |
| 即時配對型 | 整局在真實世界只過了 20–45 分鐘。若不推進價格，股價紋風不動、股票淪為呆滯資產。改為每圈跨一個交易日後，一局能回放 4 天的真實走勢。開局時決定起始日期 |

### 3.5 漲跌幅計算與防禦

```python
def daily_return(row) -> float | None:
    close = parse_price(row["ClosingPrice"])
    change = parse_price(row["Change"])
    if close is None or change is None:
        return None                    # 停牌、無成交 → 視為當日不動
    prev = close - change
    if prev <= 0:
        return None                    # 異常資料，捨棄
    r = change / prev
    return max(-0.10, min(0.10, r))    # 台股漲跌幅限制 ±10%，再夾一次防呆
```

`parse_price` 必須處理 `"--"`、`""`、`None`、含逗號的數字。**這是最容易出 production bug 的地方**——TWSE 的回傳格式在特殊交易日（如首日上市、暫停交易）會出現非預期值。

### 3.6 開發期的種子資料

**開發期不需要跑爬蟲，也不需要造假資料。**

`config/stocks.json` 的 `seed_price` 欄位存的是 **2026-08-05（民國 1150805）TWSE `STOCK_DAY_ALL` 的真實收盤價快照**——這是規劃階段實際呼叫端點取得的，不是虛構數值。

| 階段 | 股價從哪來 |
|---|---|
| P1–P4（規則引擎、UI、連線、日常型） | `config/stocks.json` 的 `seed_price` 靜態值 + 引擎內產生的隨機漲跌 |
| P5（真實數據） | 每日 `sync_stock_prices` 排程寫入 `stock_prices`，`seed_price` 僅作為初始灌庫 |

這讓 P1–P4 完全不依賴外部 API：

- 沒有網路也能跑 `make simulate`
- CI 不需要打外部服務
- 種子價是真的，所以尺度驗證（[§3.2](#32-尺度驗證)）從第一天就有效

`seed_stocks` 腳本執行時應比對現行 TWSE 清單並警告失效標的（ETF 下市與改代號比想像中頻繁）。

### 3.7 事件卡的市場干預

命運卡 F18「股災」讓該玩家所有持股當次更新額外 −8%，F19「房市降溫」讓全桌租金 −30%。

這些**只影響遊戲內狀態，不影響真實漲跌幅的套用**。實作上是在套用真實漲跌幅之後，再乘上一個事件修正係數。

## 4. 房價資料 ETL

### 4.1 資料源

內政部實價登錄提供**每季批次**下載，無官方即時 API：

- 內政部不動產交易實價查詢服務網 `lvr.land.moi.gov.tw`（原始檔下載）
- 政府資料開放平臺 `data.gov.tw`（CSV / XML / JSON）
- 各縣市政府開放資料平台（部分縣市另有自己的資料集）

原始資料是**逐筆交易**（全台一季約 10–20 萬筆），欄位包含鄉鎮市區、交易標的、交易年月日、建物型態、總價、單價、車位、建物面積等。

### 4.2 ETL 流程

```
① 下載         每季一次，全台各縣市的買賣案件 CSV
② 清洗         排除：車位單獨交易、非住宅用地、親友間交易、
                     面積 < 10 坪或 > 200 坪的極端值、
                     單價落在該鄉鎮 P5 以下或 P95 以上的離群值
③ 聚合         GROUP BY 鄉鎮市區 → 取「單價元/坪」的中位數
④ 補值         交易量 < 10 筆的鄉鎮 → 用同縣市的中位數 × 0.85 補
⑤ 分級         重算全國分位數 → 更新 price_tier
⑥ 寫入         UPSERT 到 towns 表（368 列）
```

**用中位數而非平均數**，因為單一豪宅交易會把小鄉鎮的平均值拉到失真。

**步驟 ④ 的補值是必要的**——台灣有數十個鄉鎮一季的住宅交易量是個位數（如連江縣各鄉、台東部分山地鄉），直接用中位數會極不穩定。用同縣市中位數 × 0.85 是保守估計（偏鄉通常低於縣市平均）。

### 4.3 資料量

| 項目 | 量級 |
|---|---|
| 每季下載的原始交易 | 10–20 萬筆 |
| 清洗後保留 | 約 60–70% |
| **最終寫入 DB** | **368 列** |
| 更新頻率 | 每季一次 |

**這是整個專案最輕的資料維運工作。** 原始檔不入庫，只保留聚合結果。歷史保留在 `town_price_history`（368 × 4/年 = 每年 1,472 列），供未來做「房價走勢」玩法。

### 4.4 對遊戲的影響隔離

局開始時，32 格的基價已寫入 `board_tiles` 固化（見 [03 §7.1](03-map-system.md#71-房價更新對進行中的局沒有影響)）。季度 ETL 只影響**之後開的新局**。

## 5. 排程作業

全部由 FastAPI 側的 APScheduler 執行（見 [06](06-architecture.md)）。

| Job | 排程 | 內容 |
|---|---|---|
| `sync_stock_prices` | 每交易日 15:30、16:30、17:30（重試三次） | 抓 TWSE `STOCK_DAY_ALL`，寫入 `stock_prices` |
| `check_market_open` | 每日 08:30 | 判定今日台股是否開市，寫入 `market_calendar` |
| **`daily_settlement`** | **每日 00:00** | ★ 日常型的核心排程：仲裁認購 → 退款落選者 → 未行動者執行 Standing Orders → 順位輪替 → 檢查結束條件 → 生成戰報推播 |
| `expire_trade_offers` | 每 10 分鐘 | 清理逾時的交易 offer 與關係邀請，解凍資產 |
| `blitz_turn_timeout` | 每 5 秒 | 即時配對型的 20 秒回合倒數逾時處理 |
| `etl_town_prices` | 每季 1 日 03:00 | 實價登錄 ETL |
| `send_daily_reminders` | 每日 20:00 | 對當天還沒行動的玩家推播提醒 |

**`advance_turn_windows` 已移除。** 日常型改為非同步後不再有回合時窗，所有推進集中在 `daily_settlement` 一個排程裡（見 [01 §14.3](01-game-rules.md#143-每日-0000-結算)）。

**`apply_stock_returns` 已併入 `daily_settlement`。** 因為 1 天 = 1 圈 = 1 次價格更新，兩者本來就該在同一個交易邊界內完成——分開跑會產生「價格已更新但玩家還在昨天的圈」的不一致。

`daily_settlement` 是整個日常型模式唯一的關鍵路徑，它的正確性直接決定遊戲能否進行。必須：
- 以 `pg_advisory_xact_lock` 逐局序列化
- 冪等（重跑不會重複退款或重複推進）
- 單局失敗不影響其他局

### 5.1 台股開市判定

沒有官方的交易日曆 API。判定方式：

```
呼叫 STOCK_DAY_ALL → 若回傳的 Date 欄位 == 今日（民國年格式）→ 今日有開市
                    → 若回傳的是前一交易日 → 今日休市或資料未更新
```

搭配一份**手動維護的休市日清單**（春節、國定假日、颱風假）作為快取與交叉驗證。颱風假無法預測，只能靠 API 回傳判定。

## 6. Fallback 策略

外部資料源全部有可能失效。每一個都必須有降級路徑。

| 失效情境 | 降級行為 | 玩家感受 |
|---|---|---|
| TWSE API 逾時／500 | 重試 3 次（15:30/16:30/17:30） | 無感 |
| 三次重試皆失敗 | 該日**所有股票漲跌幅視為 0** | 「今天股市沒動」，可接受 |
| TWSE 回傳部分標的缺資料 | 該標的當日 0%，其他正常 | 幾乎無感 |
| TWSE 長期失效（> 3 天） | **回放已存下的歷史交易日序列** | 走勢不再對應「今天」，但仍是真實行情 |
| 實價登錄 ETL 失敗 | 沿用上一季資料 | 完全無感 |
| 推播服務失效 | 時窗仍照常推進 | 錯過回合的人變多 |

**核心原則：外部資料源失效不能阻斷遊戲。** 所有降級路徑都指向「遊戲繼續進行，只是真實性下降」。

### 6.1 為什麼降級是回放歷史而非隨機生成

前一版設計是用各標的的歷史波動率參數生成隨機漲跌。已改為**回放已存下的歷史交易日序列**，理由：

| | 隨機生成 | 回放歷史 ✅ |
|---|---|---|
| 需要維護的參數 | 每檔的 volatility / drift（且是量級猜測） | 無 |
| 標的間的相關性 | 遺失（實際上台積電漲時聯電通常也漲） | 完整保留 |
| 資料從哪來 | 憑空 | **我們本來就每天在存** |
| 真實感 | 「像」該標的 | 就是該標的真的走過的一天 |

我們每天都在 `stock_prices` 累積資料，這份資料本身就是最好的 fallback 素材。隨機生成是在有現成資料的情況下多做一層近似，沒有必要。

降級時從歷史區間隨機挑一個起點往後回放，玩家不會看出來，且跨標的的連動關係天然正確。

## 7. 合規注意事項

本產品是遊戲，不是金融服務。以下是保持在正確一側的做法：

| 做法 | 理由 |
|---|---|
| **一律 T+1，不提供即時／盤中資料** | 這是最重要的一條。不即時就不構成報價服務，也不涉延遲揭露規範 |
| 不呈現買賣五檔、不做技術指標 | 避免形態上接近看盤軟體 |
| 遊戲幣不可儲值、不可提領、不可轉讓為法幣 | 避免博弈與虛擬貨幣議題 |
| 股市介面固定顯示免責聲明 | 明確告知性質 |
| 不提供任何「推薦」「看好」等措辭 | 避免投資建議 |
| 不使用真實個人的實價登錄門牌資訊 | 只用鄉鎮級聚合值，資料本身已去識別化 |
| 內購商品純為外觀與便利性 | 不賣數值，避免 pay-to-win 爭議 |

**遊戲幣不可提領**是最重要的一條。一旦遊戲內資產能換回真錢，整個產品的法律性質就變了。

## 8. 未來可接的真實數據（v2+）

以下不在 v1 範圍，但資料模型應預留空間：

| 數據 | 玩法 | 來源 |
|---|---|---|
| 央行利率 | 影響遊戲內貸款利率 | 中央銀行 |
| CPI 通膨率 | 影響薪資與物價的年度調整 | 主計總處 |
| 房貸利率 | 影響抵押成本 | 五大銀行平均 |
| 各鄉鎮租金行情 | 讓租金也錨定真實 | 實價登錄租賃案件 |
| 失業率 | 影響「公司裁員」事件卡的觸發率 | 主計總處 |
| 匯率 | 海外 ETF 的額外波動 | 台銀牌告 |

每一項的加入都會提高維運成本，且邊際的「真實感」收益遞減。**v1 只做股票與房價兩項，是刻意的克制。**
