# 08 — 開發路線圖

> 文件版本 v0.1｜2026-08-06
> 依使用者要求，本文件只描述**階段與交付物**，不拆 issue / milestone。

---

## 0. 排序邏輯

階段順序不是依「功能重要性」排的，而是依**「哪個決策一旦做錯，後面要重做的東西最多」**排的。

三個最貴的錯誤，以及它們對應的防線：

| 潛在錯誤 | 代價 | 防線 |
|---|---|---|
| 數值不平衡（遊戲不好玩） | 所有 UI 都要跟著調 | **P1 先做純規則引擎 + 蒙地卡羅**，UI 之前就把數值敲定 |
| 遊戲邏輯漏進 Next.js | 回合競態 + 無法離線模擬，等於重寫 | **P0 就立好 `engine/` 零 I/O 邊界**，CI 強制檢查 |
| 日常型的回合節奏不成立 | 主打模式失效，產品沒有存在意義 | **P4 獨立成一階段**，用真人跑完整 21 天局才算過 |

因此路線是：**規則引擎 → 手感驗證 → 連線 → 日常型 → 真實數據 → LINE → 商業化**。
LINE 整合排在很後面——它是獲客通路，但**在遊戲本身好玩之前，通路沒有意義**。

## P0 — 地基

**目標：讓「加一行遊戲規則」這件事有地方可以放。**

| 交付 | 內容 |
|---|---|
| Monorepo 結構 | `apps/frontend`（Next.js 15）、`apps/backend`（FastAPI + uv）、`config/`、`supabase/` |
| Makefile | `install` `dev` `build` `test` `lint` `migrate` `seed`（見 [06 §6](06-architecture.md#6-makefile)） |
| Supabase 專案 | migration 骨架、三層資料表（見 [05](05-data-model.md)） |
| Config 載入 | `config/*.json` → `game_configs` 表，含 `version` |
| CI | lint（ruff + mypy + eslint）、test、**`engine/` 的 import 邊界檢查** |
| `CLAUDE.md` | 專案鐵律 |

### P0 的關鍵動作：import 邊界檢查

```python
# CI 中執行：engine/ 不得 import 任何 I/O
FORBIDDEN = ["supabase", "sqlalchemy", "httpx", "requests", "fastapi", "asyncpg"]
```

**這條規則必須在寫第一行遊戲程式碼之前就上 CI。** 事後補救等於重構整個引擎。

**完成判準**：`make dev` 起得來、`make test` 綠燈、config 灌得進 DB。

## P1 — 規則引擎 ⭐ 最重要的階段

**目標：不碰任何 UI，就能完整跑完一局並驗證數值。**

| 交付 | 內容 |
|---|---|
| `engine/state.py` | `GameState` 不可變資料結構 |
| `engine/actions.py` | `apply_action(state, action, config) -> (state, events)` |
| `engine/board.py` | 32 格抽樣演算法 + 價格梯度排列（見 [03 §3](03-map-system.md#3-抽樣演算法)） |
| `engine/rng.py` | commit–reveal 骰子（見 [06 風險 3](06-architecture.md#風險-3--骰子公平性的信任問題)） |
| `engine/rules/` | 地產、租金、壟斷、交易、股票、職涯、車輛、保險、**借貸、監獄／醫院、家庭系統**、破產、結束條件 |
| Standing Orders 執行器 | 託管決策（見 [01 §13](01-game-rules.md#13-standing-orders預設指令)） |
| CLI 對局器 | 純文字介面，可手動或自動打完一整局 |
| `sim/` 蒙地卡羅 | `make simulate GAMES=10000` |
| 單元測試 | 每條規則的邊界情況 |

### P1 必須回答的問題

[02 §9](02-game-balance.md#11-可玩性推演) 的推演是**手算**的，而且手算過程本身就抓到兩個會讓遊戲當場壞掉的錯誤。以下必須由模擬複驗：

| # | 問題 | 通過標準 |
|---|---|---|
| 1 | 🔴 **21 圈是否放大起手優勢** | 家境與最終排名的相關係數 **日常型 < 0.35**（一格地 2.3 圈回本 × 18 圈獲利期，複利可能失控） |
| 2 | 🔴 **組隊是否過強** | 組隊者與單身者勝率差距 **< 8 個百分點** |
| 3 | 🔴 **日常型車輛是否還有意義** | 一日一圈下移動加成只減少落點數，價值主張已改變；若無意義則停用或重新定位 |
| 4 | 認購溢價是否有效抑制碾壓 | 高現金玩家的搶地成功率 < 60%；平均溢價 < 基價的 25% |
| 5 | 進修 vs 購地是否平衡 | 兩條路徑的勝率差距 < 10 個百分點（手算為 $1.20M vs $1.06M，非常接近） |
| 6 | 資產門檻公式是否恰當 | 即時配對型 15–30% 的局由門檻結束；日常型 20–40% |
| 7 | 破產會太早嗎 | 首次破產的中位數落在第 4 圈之後 |
| 8 | 順位輪替是否公平 | `base_turn_order` 與勝率的相關係數 < 0.10 |
| 9 | 30 人局撐得住嗎 | 中位局長 > 12 天；同時檢驗「起始現金 ×1.3」是否仍必要 |
| 10 | 有沒有支配性策略 | 不存在勝率 > 60% 的單一策略 |
| 11 | 監獄／醫院頻率是否合理 | 期望每年入獄 0.16 次、住院 0.27 次；玩家能感受到但不被支配 |
| 12 | 民間信貸是否成為破產主因 | 借過民間信貸者的破產率 < 借過信用貸款者的 2 倍 |
| 13 | 真實股價的尺度是否可玩 | 股票佔勝者總資產的 10–30%（太低=無用、太高=蓋過地產） |

**這十三題全部通過，才進入 P2。** 沒過就回頭調 `config/*.json` 重跑——這個循環的成本是幾分鐘，在 UI 做完之後才發現則是幾週。

**前三題是「節奏重構」引入的新風險**，第一版沒有。它們的共同點是：改制改變了時間尺度（7 圈 → 21 圈）與移動語意（多繞圈 → 少落點），使原本的平衡推導失效。完整分析見 [02 §11](02-game-balance.md#11-可玩性推演)。

若第 1 題不過（起手優勢被放大），調整優先序：**縮短局長至 14 圈 → 提高累進稅率 → 壓縮起始資產差距**。

若第 2 題不過（組隊過強），**優先調高稅率加成與家用比例，而非削弱代償**——代償是家庭系統存在的理由。

**完成判準**：`make simulate GAMES=10000 MODE=daily PLAYERS=10` 與 `MODE=blitz` 各跑完並輸出上表十三項指標，全部達標。

**P1 不需要任何外部 API。** 股價用 `config/stocks.json` 的真實收盤種子價 + 引擎內隨機漲跌即可（見 [04 §3.6](04-economy-and-realdata.md#36-開發期的種子資料)），所以 `make simulate` 離線可跑、CI 不打外部服務。

## P2 — 單機可玩（手感驗證）

**目標：確認這個遊戲用手指玩起來是舒服的。**

| 交付 | 內容 |
|---|---|
| 棋盤 UI | CSS Grid 環形（桌機）+ 捲動長條（手機） |
| 參數化 SVG | 建築 L0–L4、棋子、頭像（見 [07 §4–5](07-design-system.md#4-棋盤格的視覺編碼)） |
| 骰子動畫 | CSS 3D |
| 核心互動 | 購地、升級、抵押、抽卡、資產面板 |
| **季度事務畫面** | 通過起點的財務結算 UI（見 [01 §18](01-game-rules.md#18-季度事務)） |
| **熱座模式** | 同一裝置輪流操作，無連線 |
| shadcn 主題 | 完整 OKLCH 變數 + 深色模式 |

### ⏱️ P2 的頭號任務：實測 `SEC_PER_TURN`

**即時配對型的整個時長系統建立在「每回合平均 12 秒」這個估計值上。** 它決定了棋盤大小、圈數、以及房主看到的時長預覽是否可信。

熱座模式就是為了測它——記錄真實的每回合耗時，回頭校正 `config/endgame.json` 的 `sec_per_turn`，然後重跑 [02 §4.2](02-game-balance.md#42-即時配對型目標時長自動配置) 的全部組合驗算。

### 為什麼要做熱座模式

它不會出現在正式產品裡，但它是**唯一能在零連線複雜度下驗證手感**的方式。一台手機傳給三個朋友輪流玩，就能回答：

- 每回合實際幾秒？（校正 `SEC_PER_TURN`）
- 棋盤在手機上看得清楚嗎？
- 「一日一季」走 8–14 次擲骰要多久？會不會太冗長？
- 季度事務的資訊量會不會壓垮玩家？
- 出價認購的介面直覺嗎？（日常型的互動核心）

**完成判準**：3 個人拿一台手機打完一局即時配對型，且願意再打一局；`SEC_PER_TURN` 已用實測值取代。

## P3 — 即時配對型連線

**目標：即時多人可玩。**

| 交付 | 內容 |
|---|---|
| FastAPI 回合 API | advisory lock + `turn_seq` 樂觀鎖（見 [06 風險 1](06-architecture.md#風險-1--並發回合競態)） |
| **`RealtimeAdapter` 抽象** | 前端不直接呼叫 `supabase.channel()` |
| Supabase Realtime | 局狀態廣播、presence |
| 20 秒倒數 | 伺服器權威計時 |
| **目標時長自動配置** | 大廳選 20/30/45 分 → 即時預覽格數/圈數（見 [02 §4.2](02-game-balance.md#42-即時配對型目標時長自動配置)） |
| 即時配對 | 大廳 + 房間 |
| 玩家間交易 | 60 秒 TTL、資產凍結 |
| **季度事務側欄** | 非阻塞，可在別人回合時處理 |
| 斷線重連 | 重進即恢復 |

### P3 的兩個必測項

1. **併發競態**：腳本模擬「玩家點結束回合」與「倒數逾時」在同一毫秒觸發，重複 1,000 次，驗證回合數只 +1。
2. **`RealtimeAdapter` 的抽象是真的**：能用一個假的 polling 實作替換掉 Supabase Realtime，遊戲仍正常。這證明[風險 2](06-architecture.md#風險-2--supabase-realtime-並發連線上限) 的升級路徑是通的。

**完成判準**：6 人在不同裝置打完一局即時配對型，無狀態不一致。

## P4 — 日常型 ⭐ 主打模式

**目標：讓 30 人的群組能不卡死地玩完 21 天。**

| 交付 | 內容 |
|---|---|
| **一日一季流程** | 從目前位置擲骰前進到通過起點，沿途自動結算（見 [01 §4.2](01-game-rules.md#42-日常型一日一季)） |
| **出價認購 UI** | 出價、加價、看到誰在搶、現金凍結顯示 |
| **`daily_settlement` 排程** | ★ 每日 00:00：仲裁認購 → 退款 → 託管 → 順位輪替 → 檢查結束 → 戰報推播 |
| Standing Orders UI | 含加價規則 + 「若我今天沒上線會發生什麼」預覽 |
| APScheduler jobs | `daily_settlement`、`expire_trade_offers`、`send_daily_reminders` |
| **每日戰報 Flex Message** | 群組推播「昨日戰況」——非同步後最重要的社交鉤子 |
| offer 待辦匣 | 48 小時 TTL |
| 非常駐連線 | 開 App 拉一次狀態；出價畫面用 15 秒輪詢 |

### P4 的驗收必須是真人真時間

模擬跑不出來的東西：**人會不會真的每天回來**。

驗收方式：找 10–15 人的真實群組，跑完一整局 21 天日常型。觀察：

| 指標 | 目標 |
|---|---|
| **日活躍行動率**（親自行動，非託管） | **> 70%** |
| **競標參與率**（有無主地時實際出價） | **> 50%** |
| 每日 session 時長 | 中位數 3–5 分鐘 |
| 完局率 | 撐到結束條件觸發 |
| Standing Orders 設定率 | > 70% 的人設過至少 1 條 |

**日活躍行動率目標從 60% 上調到 70%**：非同步改制移除了「錯過時窗」這個結構性障礙，現在做不到就是內容問題，不是機制問題。

**競標參與率是新機制的專屬指標。** 若偏低，代表玩家不理解或不在乎認購制——那整個日常型的互動核心就失效了，必須重新設計出價 UI 而非加推播。

**完成判準**：一個真實群組完成 21 天局，上述指標達標。

## P5 — 真實數據

**目標：接上台股與實價登錄。**

| 交付 | 內容 |
|---|---|
| `sync_stock_prices` | TWSE `STOCK_DAY_ALL`，含 `"--"` 等髒值的防禦性解析 |
| `check_market_open` | 開市判定 + 手動休市日清單 |
| 價格推進併入 `daily_settlement` | 1 天 = 1 圈 = 1 次價格更新，同一個交易邊界內完成 |
| 股市 UI | 50 檔清單（含 12 檔主動式 ETF）、K 線、下單、持股；**在季度事務畫面內** |
| **紅漲綠跌 + ▲▼ 符號** | 見 [07 §2.3–2.4](07-design-system.md#23--台股紅漲綠跌--必須獨立的語意變數) |
| 實價登錄 ETL | 季度批次、清洗、鄉鎮中位數、補值、分級 |
| Fallback | 回放已存下的歷史交易日序列（見 [04 §6.1](04-economy-and-realdata.md#61-為什麼降級是回放歷史而非隨機生成)） |
| 免責聲明 | 股市介面固定顯示 |

### 為什麼真實數據排在 P5 而非更早

它是**話題性的來源，不是可玩性的來源**。P1–P4 用假資料（隨機漲跌 + 靜態房價）就能完整驗證遊戲。把它排在這裡，是為了不讓外部 API 的不穩定阻塞核心開發。

**完成判準**：連續 10 個交易日自動同步無人工介入；手動關掉 TWSE 存取後遊戲仍可正常進行。

## P6 — LINE 整合

**目標：打開獲客通路。**

> 完整規格見 [09-line-integration.md](09-line-integration.md)。

| 交付 | 內容 |
|---|---|
| LIFF 路由群組 | `app/(liff)/` 全 CSR（見 [06 風險 4](06-architecture.md#風險-4--liff-必須-client-side-初始化)） |
| LINE 登入 | ID token → **伺服器端驗證** → Supabase JWT |
| 群組開局 | 從 `line_group_id` 建局 + 邀請卡 Flex Message |
| 戰報 | 由 `game_events` 生成 Flex Message 圖卡 |
| `shareTargetPicker` | 跨群組分享 |
| 推播 | LINE Messaging API，**每人每局每天上限 2 則** |
| 帳號合併 | LINE ↔ email 綁定同一 `users` 列 |

### ⚠️ P6 最大的設計限制：拿不到群組成員名單

**LINE 不會給你群組的完整成員清單。** 開局必須是「貼卡片 → 大家自己點進來」的**拉**模式，不能是「讀取成員 → 自動建局」的推模式。

這影響報名階段的整個 UX 設計（等待畫面、催促按鈕、允許中途加入）。詳見 [09 §2](09-line-integration.md#2-最重要的一件事line-不會給你群組成員名單)——**這是最容易在 P6 才發現、然後整個流程重做的地方。**

### 三個會卡進度的行政流程（**P0/P4 就要啟動**）

| 項目 | 建議啟動 |
|---|---|
| 官方帳號認證（OAV） | **P0** — 需公司登記或身分文件，審核期不可控 |
| Verified MINI App 審查 | **P4** — 需先有認證帳號 |
| `shareTargetPicker` 開通 | **P4** — 需逐 channel 申請並同意 LIFF 使用條款 |

**這三件都不是技術問題，但都會讓 P6 卡住。** 未認證期間可用 Unverified MINI App 開發測試，但無法使用 In-App Purchase（影響 P7）。

### P6 的必測項

**iOS + LINE WKWebView 的 session 保持**（見 [06 風險 5](06-architecture.md#風險-5--ios-line-webview-的-session-掉失)）——這無法用桌機瀏覽器模擬，必須真機測試。

**完成判準**：從 LINE 群組貼卡片 → 5 個人各自點進來 → 開局 → 打完 → 戰報分享到另一個群組，全程無阻礙；**iOS 真機 24 小時後回來 session 仍在**（必須跨日測，這是最容易上線後才炸的一項）。

## P7 — 商業化

**目標：開始有收入。**

| 交付 | 內容 |
|---|---|
| LINE In-App Purchase | 2025 年已開放虛擬商品內購 |
| 網站金流 | 獨立網站的付款路徑 |
| 造型商店 | 頭像部件、棋盤主題、骰子特效（純 CSS/SVG，見 [07 §5](07-design-system.md#5-參數化頭像)） |
| 便利性商品 | Standing Orders 擴充至 8 條、詳細戰報 |
| 品牌置入後台 | 贊助地標建檔（見 [03 §5](03-map-system.md#5-品牌置入槽位)） |
| 分析儀表板 | 由 `game_events` 產出的留存與經濟指標 |

### 紅線

**不賣數值。** 不賣起始資金、不賣骰子點數、不賣租金加成。一旦賣數值，「經濟共生」的信條就破了——而那是這款產品唯一的差異化（見 [00 §2](00-product-overview.md#2-我們不做什麼差異化的定義來自排除法)）。

「Standing Orders 從 3 條擴充到 8 條」是這條線上最需要小心的一項。判準是：**它讓你更方便地執行你的策略，但不讓你的策略變強。** 3 條足以表達完整的保守策略；8 條只是更細緻。若實測發現付費者勝率明顯較高，就要調整（例如免費版也給到 5 條）。

**完成判準**：完成一筆真實內購；免費／付費玩家的勝率差異 < 5 個百分點。

## 階段依賴圖

```
P0 地基
 └→ P1 規則引擎 ⭐ ────────────┐
     └→ P2 單機可玩            │
         ├→ P3 即時配對型連線 ──┐   │
         └→ P4 日常型 ⭐ ───┤   │
                            ├→ P5 真實數據
                            │   └→ P6 LINE 整合
                            │       └→ P7 商業化
                            └───────┘
```

P3 與 P4 可並行（兩者都只依賴 P2），但**若資源有限，P4 優先**——日常型是主打模式。

## v1 明確排除的功能

以下都是好點子，但**不在 v1**：

| 功能 | 為什麼延後 |
|---|---|
| 跨局帳號等級／養成 | 違背[局的獨立性](00-product-overview.md#4-局的獨立性)，會擋住新人加入 |
| 觀戰模式 | 需要另一套權限模型 |
| 好友系統 | LINE 群組已經是現成的社交圖譜 |
| 排行榜賽季 | 需要防作弊機制 |
| 更多真實數據（利率、CPI、匯率） | 邊際真實感遞減，維運成本遞增（見 [04 §8](04-economy-and-realdata.md#8-未來可接的真實數據v2)） |
| 自訂棋盤編輯器 | 抽樣演算法已提供足夠變化 |
| 語音／文字聊天 | LINE 群組本身就是聊天室 |
| 融資融券、放空 | 這是遊戲不是模擬器 |
| 英文／日文版 | 地圖與數據都是台灣專屬 |
