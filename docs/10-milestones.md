## 1. ⚠️ 現況認知：所有數值都不是定稿

**`config/*.json` 與 `docs/02` 的每一個數字都是手算推導，未經任何驗證。**

它們的價值是「推導過程留下來了」，不是「這個數字是對的」。**M3 跑完蒙地卡羅之前，不要有任何人把它們當成定案。**

這直接決定了 Milestone 的排序原則：

```
規則定稿 + 能安全改數值的機制  →  實作引擎  →  用引擎跑模擬調數值  →  才做 UI
          M1                        M2            M3                     M6
```

如果順序反過來，每次調數值都要重測整條 UI 流程。

**注意 M1 包含「規則定稿」**——`docs/01` 目前是初稿，還有 14 條邊界情況沒有答案（見 [§5 M1](#m1--規則定稿--config-引擎最關鍵也最長)）。不先決定，M2 的實作者就會自己編。

## 2. ★ 最重要的一件事：Config 驅動的實作契約

你要的是「**改 JSON 不改程式碼就能改變遊戲**」。這不會自動發生——它是一個必須在 **M1 刻意設計**的架構。

### 2.1 三個層次

| 層次 | 例子 | 做得到嗎 |
|---|---|---|
| **數值可調** | 租金比例 6% → 8%、季薪倍數 3 → 2.5 | ✅ 純 JSON |
| **結構可調** | 新增一張事件卡、新增一種貸款產品、改變地產等級數量 | ✅ 純 JSON（前提是 §2.2 的設計） |
| **規則可調** | 新增一種**從未存在的效果**（如「與隨機玩家交換一格地」） | ⚠️ JSON + 一個 handler（**只加不改**） |

第三層無法純 JSON，也不該——那已經是新玩法，不是調參數。**但「只加不改」很重要**：新增效果不需要動到任何既有程式碼。

**明確做不到的：改變回合結構**（例如「一回合改成擲兩次骰」）。那是遊戲的本質，寫在引擎裡是對的。

### 2.2 四個必要元件（M1 交付）

**① Effect Registry — 效果處理器註冊表**

事件卡、落點、貸款、保險的效果**都不寫成 if/else**，而是查表：

```python
# engine/effects/registry.py
EFFECT_HANDLERS: dict[str, EffectHandler] = {}

def effect(name: str):
    def deco(fn):
        EFFECT_HANDLERS[name] = fn
        return fn
    return deco

@effect("gain")
def handle_gain(state, player, spec, ctx) -> tuple[GameState, list[Event]]:
    amount = resolve_amount(spec, player, ctx)
    return credit(state, player, amount), [Event("gain", ...)]

@effect("jail")
def handle_jail(state, player, spec, ctx): ...
```

引擎只做一件事：

```python
def apply_effect(state, player, spec, ctx):
    handler = EFFECT_HANDLERS.get(spec["type"])
    if handler is None:
        raise UnknownEffectError(spec["type"])   # 載入時就該擋掉，見 ③
    return handler(state, player, spec, ctx)
```

**新增一張卡 = 改 `events.json`。新增一種效果 = 加一個 `@effect` 函式。** 兩者都不動既有程式碼。

**② Formula Evaluator — 安全的公式求值**

`config` 裡已經有 `"formula": "NW * 0.03"`、`"6000 * (1 + move_bonus)"` 這類字串。需要一個**受限**的求值器：

```python
# engine/formula.py
ALLOWED_VARS = {"NW", "Q", "M", "base_price", "move_bonus", "avg_NW", ...}
ALLOWED_FUNCS = {"max", "min", "round", "floor", "ceil"}
# 用 ast.parse + 白名單走訪，絕不用 eval()
```

這讓「租金 = 基價 × 6%」與「稅金 = 總資產 × 4%」都能寫在 JSON 裡。

**③ Config Schema — 載入時驗證，不是 runtime 才爆**

每個 `config/*.json` 對應一份 schema（Pydantic model 或 JSON Schema）：

```
config/events.json  ←→  engine/schemas/events.py
```

驗證內容不只型別，還包括**跨檔案的不變式**：

| 檢查 | 例子 |
|---|---|
| 權重總和 | 機會卡與命運卡各為 100 |
| 效果類型存在 | 每張卡的 `effect.type` 都在 `EFFECT_HANDLERS` 裡 |
| 公式可解析 | 每個 `formula` 都能通過求值器的白名單 |
| 交叉引用 | 卡片引用的 `side_job` / `policy` 鍵都存在 |
| 棋盤自洽 | `function_tiles + property_tiles == total_tiles` |
| 版本一致 | 全部檔案的 `version` 相同 |

**`make validate-config` 是 CI 的第一道關卡。** 打錯一個鍵名，在 commit 就被擋下來，不會等到玩家開局才爆。

**④ Config Snapshot — 開局固化**

已在 [05 §1.1](05-data-model.md#11-關鍵設計開局時-snapshot-config) 定義。`game_configs` 表存整包 jsonb，開局記 `config_version`，整局讀同一份。

### 2.3 驗收標準（M1 完成的判準）

> **不改任何 `.py` / `.ts`，只改 `config/*.json`，做到以下全部：**
>
> 1. 把租金比例全部調高 20%
> 2. 新增一張事件卡「發票中千萬」（用既有的 `gain` 效果）
> 3. 刪除「民間信貸」這個貸款產品
> 4. 把地產等級從 5 級改成 4 級
> 5. 新增一個縣市到六大區域的分組
>
> 每一項改完 `make validate-config` 通過、`make simulate` 跑得動、數值有反映變化。

**這五題做不到，M1 就沒完成。** 之後每一個 milestone 都建立在它上面。

## 3. 股市：建議全程使用機率模型

你提到「考慮股市直接不接即時，用機率方式造成波動」——**建議更進一步：真實資料延到最後，且永遠設為可選。**

### 3.1 理由

| 論點 | 說明 |
|---|---|
| **玩家分辨不出來** | 「台積電今天 +2.1%」與「一個合理的隨機漲跌」在遊戲體驗上沒有差別 |
| **真實資料的價值是行銷不是玩法** | 「跟真實台股連動」是文案賣點，不是讓遊戲變好玩的東西 |
| **它是外部依賴** | TWSE 無 SLA、會有髒值、會下市改代號。讓核心開發依賴它是不划算的 |
| **機率模型更好平衡** | 波動率可控 → 蒙地卡羅可重現 → 數值調得準 |

### 3.2 做法：同一個介面，兩種實作

```python
class PriceProvider(Protocol):
    def advance(self, game_id: str, lap: int) -> dict[str, Decimal]: ...

class SimulatedPriceProvider:      # M1 起使用，永遠可用
    """依各標的的 volatility / drift 生成日漲跌，夾在 ±10%"""

class TwsePriceProvider:           # M9 才實作，可選
    """讀 stock_prices 表的真實收盤序列"""
```

- **M1–M8 全部用 `SimulatedPriceProvider`** —— 離線可跑、CI 不打外部服務、模擬可重現
- **M9 才實作 `TwsePriceProvider`**，且由 config 一個開關切換
- `config/stocks.json` 的 `seed_price`（2026-08-05 真實收盤快照）作為兩者共同的起點

### 3.3 對現有文件的影響

[04-economy-and-realdata.md](04-economy-and-realdata.md) 描述的真實資料接入**全部保留**，但降級為 **M9 的可選功能**而非核心路徑。文件裡的 fallback 策略（回放歷史序列）與此一致。

**與 Roadmap 的順序差異有兩處，都是刻意的：**

1. **M5（登入/Onboarding）提前到 UI 之前** —— Onboarding 本身就是第一批畫面，且在真實 session 上蓋 UI 比事後補 auth 少很多返工
2. **M7（日常型）排在 M8（即時配對型）之前** —— 日常型是主打模式，且非同步比 Realtime 簡單，先做能更早拿到真人回饋

### ⚠️ 常見誤讀：「數值處理好才進遊戲核心」

**不是。** 正確順序是：

```
M1  Config 機制（不含數值）
     ↓
M2  ★ 遊戲核心引擎  ← 核心在這裡，不在最後
     ↓
M3  用 M2 的引擎跑模擬，把數值調對
```

**M1 只建立「能安全改數值的機制」，不決定任何數值。** 而 M3 的數值**必須有引擎才調得動**——調數值靠的是跑一萬局模擬，沒有 M2 就沒得跑。

比喻：M1 是裝插座、M2 是接上電器、M3 是通電後量電壓。

### M3 與 M9 的差別

兩者都叫「數據」，但完全是不同的東西：

| | **M3 數值定稿** | **M9 內容與資料** |
|---|---|---|
| 處理什麼 | **遊戲設計參數**：租金 6%、季薪倍數 3、結束門檻公式 | **外部真實資料**：信義區實際均價、台積電收盤價 |
| 怎麼決定 | 跑一萬局模擬調出來 | 從內政部／TWSE 抓下來 |
| 性質 | **設計問題** | **工程問題** |
| 錯了會怎樣 | 遊戲不好玩 | 地名價格不真實，但遊戲照跑 |
| 誰是權威 | 蒙地卡羅的輸出 | 政府與交易所 |

**M2/M3 期間用假鄉鎮資料就能跑。** 隨機生成 40 個「XX 區．均價 25 萬」的合成資料，模擬完全成立——因為模擬要驗證的是「租金比例對不對」，不是「信義區是不是真的 110 萬」。

M9 只是把假的換成真的。

### M1 — ★ 規則定稿 + Config 引擎（最關鍵、也最長）

**目標：把規則決定完，並讓「改規則」= 「改 JSON」。**

#### 為什麼這兩件事綁在一起

不是為了省 milestone。**寫 config schema 會逼你把邊界情況決定完**——你沒辦法定義「認購」的資料結構，卻不回答「得標者在結算前破產怎麼辦」。

Schema 是規則的**形式化**。規則沒想清楚，schema 就寫不出來；schema 寫得出來，代表規則想清楚了。

### ⚠️ 規則不是在 M1 就「定稿」完

M1 只能決定**紙上決定得了的部分**。規則實際上會在三個地方被推翻：

| 階段 | 推翻什麼 | 為什麼 |
|---|---|---|
| **M1** | 邊界情況、範圍 | 形式化會逼出矛盾 |
| **M2** | 實作矛盾 | 寫程式碼會發現「這兩條規則不能同時成立」 |
| **M3 / M6** | 平衡假設 | 模擬與試玩會證明「這條規則不好玩」 |

所以 M1 的「定稿」意思是**凍結一個可實作的版本**，不是「永遠不改」。有 M1 的 config 機制在，後面兩階段的改動成本才會低。

## 7. 後續怎麼改規則而不用大改文件

**這是你最後一個問題，也是最重要的一個。**

### 7.1 三份東西的權責

| | 角色 | 改動成本 |
|---|---|---|
| `config/*.json` | **數值與結構的 SSOT** | 低——這是設計來被改的 |
| `docs/01` | **機制的 SSOT**（規則怎麼運作） | 中——只在機制真的變了才改 |
| `docs/02` | **數值的說明與推導**（為什麼是這個數字） | 低——但容易與 config 漂移 |

### 7.2 防止漂移的三個機制

**① `docs/02` 的表格由 config 產生，不手動維護**

```bash
make sync-balance-doc   # 讀 config/*.json → 重新產生 docs/02 的數值表格
```

`docs/02` 保留**推導與理由**（人寫），數值表格**自動生成**（機器寫）。這樣改一個數字不會留下十個過時的文件段落。

> 這次改制手動同步了 46 張卡片與十幾張表，很花時間也容易漏。這個工具應該在 M1 就做。

**② config 是唯一真相，文件引用它而非複製它**

文件裡寫「租金 = 基價 × `properties.json:levels[].rent_ratio`」比寫死「6%」好。已經有的表格保留（可讀性重要），但由 ① 自動同步。

**③ 變更分級，決定要改多少東西**

| 變更類型 | 要改什麼 |
|---|---|
| 調一個數值 | `config/*.json` + `make sync-balance-doc` |
| 新增一張卡 / 一種貸款 | `config/*.json`（+ 自動同步） |
| 新增一種效果類型 | config + 一個 `@effect` handler |
| 改變一個機制 | config + `docs/01` 對應章節 + engine 規則 |
| 改變回合結構 | **全部**——這是重大改版，應該慎重 |

**前兩級應該佔 90% 的變更。** 如果實際上常常需要動到後兩級，代表 M1 的抽象做得不夠。

### 7.3 現在就該接受的事

**這批文件會過時，而且應該過時。** 它們的價值是：

- 把設計理由留下來（為什麼是 21 圈、為什麼溢價不計入市值）
- 讓 M1–M3 有東西可以實作與驗證

**M3 跑完蒙地卡羅後，`docs/02` 的數值必定會被改寫一輪。** 那不是文件寫壞了，那是流程正常運作。
